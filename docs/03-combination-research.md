# 組み合わせ利用の可能性 — 研究ノート

本 LP のメインテーマ。「25 機能をどう組み合わせられるか / どこに限界があるか」を、
実ソース解析にもとづいて整理する。**未検証の仮説には ❓ を付し、検証計画を末尾に置く。**

---

## 1. 組み合わせを可能にする構造的前提

### 1-1. Wrapper 系は `children` を取る → **入れ子が文法的に成立する**
22 種すべてが `interface XxxProps extends XxxOptions { children: ReactNode; ... }`。
つまり次はコンパイルが通る:

```tsx
<VHS>
  <Glass>
    <h1>Canvas UI</h1>
  </Glass>
</VHS>
```

### 1-2. 出力キャンバスは `pointer-events: none`
効果レイヤーはイベントを一切捕まえない。何段重ねても、クリック・選択・入力は
最下層の本物の DOM に届く。**入れ子にしてもインタラクティブ性は失われない。**

### 1-3. イベント購読先はラッパー自身のルート要素
```ts
const listenTarget = output.parentElement ?? output;   // = ラッパーの <div>
```
子孫で起きた `pointermove` はバブリングで**各段のラッパーに届く**。
→ 入れ子の外側・内側が**同時に**カーソルへ反応する（無効化されない）。

### 1-4. 仕様上、ネスト自体は禁止されていない ❓
WICG の HTML-in-Canvas 仕様は、複数の `<canvas layoutsubtree>` による同時キャプチャを
想定しており、明示的なネスト制限は見当たらない（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。
ただし**「内側のラッパーが出力した WebGL キャンバスの中身を、外側が正しく取り込めるか」**は
別問題で、**実機検証が必須**（→ 検証計画 T-2 / T-3）。
※ 旧来の html2canvas では入れ子 `<canvas>` は空白になる既知問題があり、同じ轍を踏む可能性は残る。

## 2. 組み合わせパターンの分類

| ID | パターン | 概要 | リスク | 推奨度 |
|---|---|---|---|---|
| **P1** | **逐次（セクション分割）** | 1 セクション 1 エフェクト。スクロールで切り替え | 低 | ★★★ 基盤 |
| **P2** | **入れ子スタック** | `<A><B>content</B></A>` で効果を積む | 中〜高 | ★★☆ 研究の主題 |
| **P3** | **Object を Wrapper に内包** | three.js キャンバスを html-in-canvas で包む | 高 ❓ | ★★☆ 最も面白い |
| **P4** | **空間的並置** | 同一ビューポート内に横並び・グリッド配置 | 中（予算） | ★★★ |
| **P5** | **状態駆動スワップ** | 同じ内容にかけるエフェクトを操作で差し替え | 低 | ★★★ 展示向き |
| **P6** | **パラメータ融合** | 1 コンポーネントのオプションで複合表現を作る | 最低 | ★★★ |

### P6 が意外に強い
`Frost` は 27 options、`Magnify` は 21 options、`GlassObject` は 29 options を持つ（全体で **409 options**）。
たとえば `Glass` に `blur`（フロスト化）+ `aberration`（色収差）+ `zoom` + `targets` を同時指定すれば、
**単体で「Glass × Frost × Magnify」相当の見た目**になる。
→ **重ねる前に、まず 1 つのコンポーネントを詰めるべき。** WebGL コンテキストを 1 つしか使わない。

## 3. コンポーネントの相互作用プロファイル

組み合わせの相性は「入力の奪い合い」で決まる。イベント購読を全数調査した結果:

### 3-1. アンビエント型（ポインタ入力なし）— **積み重ねに最も安全**
`Blaze` `Glitch` `VHS` `DitheredObject` `GlassObject`
→ カーソルと無関係に動くので、**どのレンズ型とも競合しない**。組み合わせの土台に最適。

### 3-2. レンズ型（カーソル追従・局所効果）— **同種どうしは競合**
`Glass` `Magnify` `Bubble` `RetroDither` `Asciify` `ParticleReveal`
→ 2 つ重ねると**カーソル位置に 2 つの円が重なり**、意味的に破綻しやすい。
   組み合わせるなら「サイズを大きく変える」「片方の `follow` を下げて遅延させる」。

### 3-3. 撹乱場型（カーソルで場が乱れる・全面効果）
`Liquid` `Ripple` `Frost` `Cloth` `Grid` `Shatter` `Droplets` `Clouds` `HexFloat` `Peel` `Bend`
→ アンビエント型・レンズ型とは相性良好。同型どうしは**ジオメトリの奪い合い**になる（後述 R4）。

### 3-4. スクロール駆動型 — **同時使用は原則不可**
`Laser`（下端で内容を隠す）/ `ParticleScroll`（境界線から下を砂に）/ `Bend`（スクロールで折り曲げ）
→ 3 つとも**スクロール量でコンテンツの見え方を占有**する。同一セクションでの併用は避ける。

### 3-5. テーマ追従型（`prefers-color-scheme` を購読）
`Asciify` `Cloth` `Clouds` `Peel` — ダークモードで自動的に色を変える。
`"auto"` 系オプション（`background` `backing` `gapColor` `shineColor`）も**ページ背景をサンプリング**する。
→ **入れ子にすると、外側が背景を変えてしまい `"auto"` の判定が壊れる ❓**（→ T-5）
   対策: 入れ子で使う場合は `"auto"` を使わず **RGB を明示指定**する。

## 4. リスク登録簿

| ID | リスク | 深刻度 | 根拠 | 対策 |
|---|---|---|---|---|
| **R1** | **WebGL コンテキスト予算の枯渇** | **致命的** | 1 コンポーネント = 1 WebGL2 コンテキスト。Chrome の上限は概ね 16 前後で、超過すると古いものから強制的に失われる | §5 参照 |
| **R2** | **コンテキストロストから復帰しない** | **致命的** | `webglcontextlost` ハンドラが **0/25**。失われたら黒画面のまま | 同時マウント数を予算内に抑える（唯一の対策） |
| **R3** | 入れ子でのフレームコスト増 | 高 | N 段 = 毎フレーム N 回の DOM ラスタライズ + テクスチャ転送 | 入れ子は **2 段まで**を上限に |
| **R4** | ジオメトリ変形の二重適用 | 中 | `Shatter` `Grid` `Bend` `Peel` `HexFloat` は座標を作り替える。重ねると位置が二重にズレ、可読性が崩壊 | 同カテゴリを重ねない |
| **R5** | `"auto"` 背景サンプリングの誤判定 | 中 | 外側の効果が背景を塗り替えるため | RGB 明示指定 |
| **R6** | 可読性・アクセシビリティの劣化 | 中 | 破壊系（`Glitch` `VHS` `RetroDither` `ParticleReveal`）の重ねがけで本文が読めなくなる | 破壊系は**装飾領域のみ**。本文には 1 段まで |
| **R7** | 非対応ブラウザでの見え方 | 低 | 入れ子でも各段が独立に素の HTML へフォールバック。**内容は必ず読める** | 告知バナーで補足 |

## 5. WebGL コンテキスト予算 — 本 LP 最大の設計制約

### 問題
25 種すべてを 1 ページに常時マウントすると、**25 個の WebGL2 コンテキスト**を要求する。
Chrome の同時コンテキスト上限（概ね 16）を超えると古いものから破棄され、
`webglcontextlost` ハンドラが無いため**そのセクションは二度と復帰しない**。

### 重要な区別: 「停止」は「解放」ではない ⚠️
全 25 本が `IntersectionObserver` で**画面外では描画を止める**が、
これは rAF を止めるだけで、**WebGL コンテキストは保持したまま**。
→ **スクロールしても予算は減らない。**

### 対策: 条件付きマウント／アンマウント
幸い、全 25 本が `destroy()` で texture / program / shader / buffer を完全に解放する
（クリーンアップ実装は 25/25 で確認済み）。したがって:

```
IntersectionObserver で「画面から N 画面分離れたセクション」を
React 側で条件付きレンダリングから外す → コンテキストが実際に解放される
```

- 目標: **同時マウント 6〜8 個以内**（安全マージン込み）
- 実装は `<Section>` ラッパー 1 つで共通化でき、25 セクション全部に効く
- Object 系（three.js）も 1 つずつコンテキストを消費するので同じ予算に含める

**この「マウント管理レイヤー」が、LP 実装で最初に作るべきコア部品。**

## 6. 有望な組み合わせ候補（研究テーマ）

### 6-A. アンビエント × レンズ — **本命。競合しない**
| 組み合わせ | 狙い |
|---|---|
| `VHS` × `Glass` | 劣化したテープ映像を虫眼鏡で覗く。ノイズ越しに一点だけ光学的に読める |
| `Blaze` × `Asciify` | 炎の熱で文字がアスキーへ崩れる。熱 → 情報の劣化という比喩 |
| `Glitch` × `Magnify` | 崩れた信号を HUD スキャナで解析している画。SF 的整合性が高い |
| `Clouds` × `RetroDither` | 霧の中をレトロ画面で覗く |

### 6-B. Object 系 × Wrapper 系（P3）— **最も新規性がある** ❓
```tsx
<Ripple>
  <GlassObject src="/models/logo.glb" />
</Ripple>
```
three.js の 3D オブジェクトを、水面の屈折越しに見る構図。
**成立すれば LP の目玉になる**が、`drawElementImage` が内側の WebGL キャンバスの
ピクセルを取り込めるかに全面的に依存する。→ **検証 T-3 が最優先**。
不成立でも **P4（並置）** に退避すれば絵は作れる。

### 6-C. スクロール駆動 × アンビエント
`Laser` × `Blaze` / `ParticleScroll` × `Clouds`
→ スクロール駆動型は 1 セクション 1 つ厳守。アンビエントとだけ重ねる。

### 6-D. 避けるべき組み合わせ
| 組み合わせ | 理由 |
|---|---|
| `Shatter` × `Grid` × `HexFloat` | ジオメトリ三重適用（R4）。破綻確実 |
| `Glass` × `Magnify` | レンズ二重（3-2）。カーソルに円が 2 つ |
| `Laser` × `ParticleScroll` × `Bend` | スクロール占有の三つ巴（3-4） |
| 破壊系 × 破壊系 を本文に | 可読性喪失（R6） |

## 7. 検証計画（実装前に潰すべき項目）

Chrome Canary 149+ / `chrome://flags/#canvas-draw-element` 有効 で実施。
**各項目は最小再現ページ 1 枚で確認でき、LP 本体の実装より先に行う。**

| ID | 検証項目 | 判定基準 | 失敗時の代替 |
|---|---|---|---|
| **T-1** | 単体動作のベースライン | 25 種すべてが単体で描画される | 個別に除外 |
| **T-2** | Wrapper 2 段の入れ子 | 外側が内側の効果を取り込んで描画する | P2 を捨て P4/P5 へ |
| **T-3** | **Object 系を Wrapper に内包** | three.js キャンバスの中身が外側に映る | 並置（P4）へ退避 |
| **T-4** | 入れ子 3 段のフレームコスト | 60fps 維持できるか | 2 段上限を確定 |
| **T-5** | `"auto"` 背景の入れ子挙動 | 色が破綻しないか | RGB 明示を全面採用 |
| **T-6** | **同時マウント数の上限測定** | 何個目でコンテキストロストが起きるか | 予算値を確定（最重要） |
| **T-7** | マウント／アンマウント往復 | 解放後に再マウントして復帰するか | 予算内固定配置へ |
| **T-8** | 非対応ブラウザ（Safari/Firefox） | 全セクションが素の HTML で読めるか | 個別フォールバック追加 |
| **T-9** | `prefers-reduced-motion` | 全 25 種でモーションが抑制されるか | 静止画差し替え |

### 検証の順序
```
T-6（予算）→ T-1（単体）→ T-3（Object内包）→ T-2（2段）→ T-4/T-5 → T-7 → T-8/T-9
```
T-6 と T-3 の結果で **LP の骨格が決まる**ため、最初に実施する。

### 【最重要】T-2 不成立 / T-3 成立 — 入れ子の可否が確定した

| 構成 | 結果 | 観察 |
|---|---|---|
| `VHS › Glass › HTML` | ❌ | レンズ内が**完全に黒**。下の見出しが消える。レンズ外では VHS は正常に効いている |
| `Glass › VHS › HTML` | ❌ | 外側 Glass は正常（レンズ内で文字が拡大・色収差あり）。**内側 VHS は完全に消失**（レンズ外の文字にノイズが無い）。レンズ内部も黒 |
| `VHS › GlassObject` | ✅ | 3D の星が**テープ揺れと色滲みを受けて表示**される。fps 91〜110 |

**結論: html-in-canvas どうしの入れ子は composition しない。**
内側ラッパーの WebGL 出力は、外側の `drawElementImage` に**黒として取り込まれる**（あるいは
内側が自分の内容を捕捉できずに黒を描く）。双方向で再現したため、順序の問題ではない。

一方 **Object 系（three.js）は入れ子にできる**。three.js の canvas は
`layoutsubtree` による入れ子キャプチャを伴わないため、外側から普通の canvas として取り込まれる。

LP を通しスクロールし、受入シナリオ **ST-05 / AC-10** を実施した。

→ **合格**。Origin Trial が無い通常の Chrome でも内容がすべて読め、
予算超過も描画失敗も発生しない。

### T-6 の詳細

```
同時に生存できた WebGL2 コンテキスト数 : 16
停止理由 : 17 個目の生成時に、1 個目のコンテキストが失われた
推奨 capacity（実測の 55%）: 8
```

**調査段階の予測と完全に一致した。**
- 上限が概ね 16 であること
- **古いものから破棄される**こと（17 個目の生成で 1 個目が失われた）

→ **`BudgetConfig.capacity = 8` を確定値とする**（未決 D-1 解消 / REQ-4.2）。
`DEFAULT_SELECT_CONFIG.capacity` の初期値 8 は妥当だったため、実装の変更は不要。

### T-9 の詳細（reduced-motion）

`prefers-reduced-motion: reduce` を有効にした Chrome 150（フラグ有効）で実施。

```
自動検証   : 25/25 OK・噛んだ 22 / Object 3・NG 0・fps 119〜121
通しスクロール: 29,150px / 96 サンプル・最大 active 4/8・失敗 0・CLS 0
本文       : 11,136 文字（すべて読める）
```

**抑制の仕組み**（ソースで確認）— 25 本すべてが `matchMedia` を購読し、2 通りに分岐する。

| 型 | 挙動 |
|---|---|
| アンビエント型（`VHS` `Blaze` `Glitch` `Clouds` 等） | `if (!reducedMotion) time += delta * speed` で**時間が進まなくなる**。さらに `reducedMotion && !contentDirty` で**再描画自体をスキップ**する |
| カーソル追従型（`Glass` 等） | イージング係数が 1 になり、**補間アニメーションなしで即座に追従**する |

**実証**: `VHS` セクションを 2 秒あけて 2 回撮影したところ、
**ノイズパターン（色滲み・テープ揺れ）が完全に同一**だった。
動作中なら毎フレーム変化するため、時間が凍結されていることの直接的な裏づけになる。

> ⚠️ **fps では判定できない。** ページ側の rAF は 120fps のまま回るため、
> fps を見ても抑制の有無は分からない。ソースの機構確認とフレーム比較の 2 つで判定した。

### T-8 の詳細（非対応環境でのフォールバック）

検証ハーネスの「自動検証」で 25 種を 1 つずつマウントし、機械判定した結果:

```
Wrapper 系 22 種 : すべて「フォールバック」（html-in-canvas が噛まず素の HTML へ）
Object  系  3 種 : すべて「OK」（three.js のみに依存するため描画された）
NG（例外・canvas 未生成）: 0 件
最低 fps : 37
```

**REQ-5.1 / 5.2 / 5.7 が実証された。**
- 非対応環境で全セクションの内容が読める。エラー・空白領域は発生しない
- Object 系 3 種は非対応環境でも通常どおり動作する

> なお最低 fps 37 は、自動検証が three.js のシーンを連続生成した際の値。
> 通常のセクション表示時の性能は PT-01 で別途測定する。

**実機（Chrome 149 / macOS）でも再測定し、同一の結果を得た。**

| 環境 | 同時生存 | 停止理由 | 推奨 capacity |
|---|---|---|---|
| 開発機の内蔵ブラウザ | 16 | 17 個目で 1 個目がロスト | 8 |
| **Chrome 149（実機）** | **16** | **17 個目で 1 個目がロスト** | **8** |

2 環境で一致したため、`capacity = 8` を確定値とする。
55% の安全マージンは GPU・同居 canvas による変動を吸収するためのもの。

## 8. 現時点の設計結論

1. **基盤は P1（セクション分割）+ 条件付きマウント管理**。これが無いと 25 機能の展示は成立しない
2. **「組み合わせ」の主役は P6（パラメータ融合）と 6-A（アンビエント × レンズ）**。低リスクで効果が高い
3. **P2 / P3 は研究枠**。検証 T-2 / T-3 の結果次第で目玉にも没にもなる。**LP の必須要件には置かない**
4. **入れ子は 2 段まで**を暫定ルールとする（T-4 で確定）
5. 組み合わせるときは **`"auto"` を使わず色を明示**する
