## 1. テスト方針

| # | 方針 | 理由 |
|---|---|---|
| **TP-1** | **`selectPhases` の単体テストを品質の中心に置く** | ここが正しければ AC-1〜3 は構造的に満たされる。逆にここが誤ると LP 全体が破綻する |
| **TP-2** | **自動化できるものは自動化し、WebGL の見え方は手動に委ねる** | 描画結果の自動判定は費用対効果が低い。画素比較は環境差で不安定 |
| **TP-3** | **各ゲートは「合格した項目の記録」をもって通過とする** | 実施の有無が曖昧なまま次段階に進まない |
| **TP-4** | **非対応環境のテストを対応環境と同格に扱う** | P2 が訪問者の多数派（`requirements.md` §4）。※ 対象ブラウザは Safari と通常 Chrome。Firefox は対象外（§3） |
| **TP-5** | **不合格時は仕様側の逃げ道を先に確認する** | REQ-2.8 / REQ-10.6 など、条件付き要件が既に用意されている |

## 4. M0 のテスト項目 — 共通基盤と検証

### 4.1 単体テスト: `selectPhases`【最重要】

共通の設定値: `capacity=3, activateDistance=1.0, releaseDistance=2.0, prefetchDistance=3.0, incumbentBonus=0.5`

| ID | 検証内容 | 入力 | 期待結果 |
|---|---|---|---|
| **UT-01** | 候補ゼロ | `[{a, 5.0, dormant}]` | `a: dormant` |
| **UT-02** | 候補 < capacity | `[{a,0.1,dormant},{b,0.5,dormant}]` | 両方 `active` |
| **UT-03** | 候補 > capacity | `[{a,0.1},{b,0.2},{c,0.3},{d,0.4}]` 全て dormant | `a,b,c: active` / `d: preloading` |
| **UT-04** | **starvation 回避** | 現役 3 件が `1.8/1.9/1.95`（active）、新規 `0.1`（dormant） | 実効距離は現役 `1.3/1.4/1.45`、新規 `0.1`。→ **新規が `active`、最遠の現役（1.95）が押し出され `preloading`** |
| **UT-05** | capacity の実行時減少 | 現役 3 件 active、`capacity` を 1 に変更 | 最も近い 1 件のみ `active`、他は解放 |
| **UT-06** | 未測定 | `[{a, Infinity, dormant}]` | `a: dormant` |
| **UT-07** | 全て failed | `[{a,0.1,failed},{b,0.2,failed}]` | 全て `failed`、`active` は 0 件 |
| **UT-08** | 同値の決定性 | `[{b,0.5,dormant},{a,0.5,dormant}]`、capacity=1 | `a: active`（id 昇順） |
| **UT-09** | 不変条件 I-1 | ランダム 100 件 × 100 試行 | `active` 数が常に `capacity` 以下 |
| **UT-10** | 不変条件 I-2 | `failed` を含む任意の入力 | `failed` は他フェーズに遷移しない |
| **UT-11** | 不変条件 I-3 | 現役だが `distance=2.1` | `active` にならない |
| **UT-12** | 不変条件 I-4 | 同一入力で 2 回実行 | 出力が完全一致 |
| **UT-13** | 不変条件 I-5 | `capacity=0` | `active` 0 件 |

> **UT-04 が本アルゴリズムの核心。** ここが落ちると、画面中心のセクションが
> 永久に活性化されない不具合になる。実装前にこのテストを書くこと。

### 4.4 技術検証（手動 / `lab.html` / 環境 E1）

**M0 の主目的。** 結果は `docs/03-combination-research.md` §7 に記入する。

| ID | 検証 | 手順 | 合格基準 | 不合格時 |
|---|---|---|---|---|
| **T-6** | **同時マウント上限の実測** | `ContextBudgetProbe` で WebGL2 コンテキストを逐次生成し、生成失敗または既存のロストが起きた個数を記録 | 実測値が数値で得られる。**その 50〜60% を `capacity` に採用** | R-1: ステージ構成を見直す |
| **T-1** | 単体動作の基準 | 25 種を 1 つずつ表示 | 25 種すべてが描画される | 動かない種を個別に除外 |
| **T-3** | **Object 系を Wrapper に内包** | `NestingProbe` で `Ripple > GlassObject` を表示 | 内側の three.js 描画が外側の効果に取り込まれる | R-2: 並置（P4）へ退避。REQ-2.8 発動 |
| **T-2** | Wrapper 2 段の入れ子 | `VHS > Glass` 等を 2 例以上 | 外側が内側の効果を取り込んで描画 | R-3: REQ-10.6 により「並置」へ読み替え |
| **T-4** | 入れ子 3 段のコスト | 段数を 1→2→3 と変え fps を記録 | 2 段で 50fps 以上。3 段の可否を判定 | 上限段数を確定（既定 2 段） |
| **T-5** | `"auto"` 背景の入れ子挙動 | `MatrixProbe` で `"auto"` と RGB 明示を並置 | 色の破綻有無を記録 | RGB 明示を全面採用（既に N-4 で規定） |
| **T-7** | マウント往復 | `MatrixProbe` で 50 回反復 | 毎回正常に復帰。黒画面ゼロ | 予算内固定配置へ方針変更 |
| **T-8** | 非対応ブラウザ | E2 / E3 で `lab.html` を開く（E4 Firefox は対象外） | エラーなく素の HTML。Object 系は動作 | 個別フォールバックを追加 |
| **T-9** | reduced-motion | E7 で全 25 種を表示 | 全種でモーションが抑制される | 該当種に静止表示を追加 |

**実施順序**: `T-6 → T-1 → T-3 → T-2 → T-4 → T-5 → T-7 → T-8 → T-9`

### Safari 26.3 の実測（環境 E3 / 2026-07-26）

```
html-in-canvas : 無効
ok 3 / fallback 22 / NG 0     ← 期待値と完全一致
Object 系 3 種 : すべて OK（GlassObject / ParticleObject / DitheredObject）
fps            : 48〜61（hex-float のみ 31）
```

**REQ-5.1 / 5.2 / 5.7 が Safari でも実証された。** 例外ゼロ、canvas 未生成ゼロ。

> **`hex-float` の 31fps について（LP の性能ではない）**
> Canvas UI の `createGlass` 等は WebGL さえあれば**非対応環境でも WebGL ループを回す**
> （`htmlInCanvas` が false でも `createXxx` は null を返さない）。
> 自動検証は対応可否に関わらず 25 種をマウントするため、Safari でも WebGL が動き、
> 最も重い `HexFloat`（ソース 50KB）で 31fps まで落ちた。
>
> **LP 本体では発生しない。** `EffectSection` の
> `shouldApply = phase==="active" && !disabled && (family==="object" || supported)`
> により、非対応環境で Wrapper 系は**そもそもマウントされない**。
> Safari の LP が抱える WebGL コンテキストは Object 系 3 種のみ。

### PT-04 メモリ 10 分（環境 E1 / 2026-07-26）

LP を 10 分間（605 秒）通しスクロールし続けた結果。**71 往復**（上下 1 回で 1 往復）。

```
最大 active     : 4 / 8      失敗: 0
ヒープ          : 開始 34.1MB → 終了 39.8MB（最小 32.6 / 最大 54.3）
傾き            : +0.61 MB/分
71 往復後の構造 : section 27 / canvas 10 / DOM 1,068 ノード / 生存 WebGL コンテキスト 4
```

**判定: 合格。** NFR-1.5 の意図は「アンマウント時にリソースが解放されること」であり、
71 往復後も **section 27・canvas 10・生存コンテキスト 4 のまま増えていない**。
DOM ノードも 1,068 で有界。**構造的な蓄積はゼロ**で、解放が機能している。

> **数値は正直に記録する。** ヒープは +0.61MB/分の緩やかな上昇がある。
> ただし途中で 40.4 → 37.2MB まで落ちる場面が複数あり（のこぎり波）、GC は機能している。
> ヒープ上限 4,192MB に対し 40MB は 1%。実利用（数分の閲覧）で問題になる水準ではない。
> **単調増加している場合に疑うべき「構造の増殖」は起きていない**ことを上の 4 指標で確認した。
